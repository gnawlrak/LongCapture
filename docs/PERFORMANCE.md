# 性能排查

## 区分三种状态

- **只剩菜单栏、没有采集**：不会创建屏幕流或拼接任务；框选但尚未开始也不启动屏幕流。
- **正在采集但没有滚动**：仍会接收系统提供的完整帧。完全相同的可靠帧不重新配准；匹配暂停后完全不变的失败帧也不重新配准或搜索历史。
- **开发测试**：完整 XCTest 会启动独立调试身份的测试宿主，执行大量 Vision 和逐像素检查，可能显示为同名 `LongCapture` 进程。应核对 PID 与可执行文件路径，不能把测试宿主和菜单栏 Release 当成同一进程。

完成或取消会停止屏幕流；完成先处理尾帧，再交付结果。迟到回调不能重新启动采集或修改已完成的结果。生命周期单元测试使用注入来源，不等同于真实 ScreenCaptureKit 在所有系统上的资源测量。

## 2026-10-30 排查记录

用户报告不用时 CPU 很高。本次没有复现**纯待机持续高占用**：

- 对运行中的 build 2 Release 进程连续采样约 10 秒，6 次 CPU 读数均为 0.0%，CPU 累计时间不变；另取 5 秒调用栈，主要线程在系统事件等待中。
- 随后运行中的 build 3 Release 进程另测约 30 秒，16 次读数中 13 次为 0.0%，其余为 0.1%、0.8%、1.8%；累计 CPU 时间增加约 0.06 秒。期间未强制停止进程或更改用户授权。该区间没有复现持续高 CPU，不能证明所有使用后的状态都无问题。
- 以上运行包尚不包含本次失败帧优化，不能将其低占用归功于修复。也不能仅凭测试会高占用，就认定测试是用户原症状的根因。
- 安装并正常重启本次构建后，再测约 20 秒，11 次 CPU 读数全部为 0.0%，累计 CPU 时间不变，约 13MB 驻留内存。这只补充该次菜单栏待机测量，不把未复现的原症状记作已修复。

另确认了一个独立问题：进入匹配暂停后，未改变的失败画面每次都会重复执行昂贵配准／恢复。现在只记住最近失败帧的尺寸与整帧 SHA-256，不保留额外视口；相同失败画面继续提示恢复，但不重复配准。任意像素或尺寸改变都会重新检查，恢复后清除指纹。指纹只用于避免重复失败工作，**绝不用于批准位移、跳过接缝或增加输出像素**。

## 再次出现时取证

请先记下状态：只剩菜单栏，还是采集工具条仍显示；是否有“匹配暂停”、预览或设置窗口。不要通过上传私人截图来复现。

活动监视器中选中对应进程 → 取样进程，或者在终端先确认 PID 和可执行文件路径：

```sh
pgrep -x LongCapture
# 将 12345 替换为对应 PID；同时有调试测试宿主时逐个核对路径
ps -p 12345 -o pid,%cpu,time,etime,comm
top -l 6 -s 2 -pid 12345 -stats pid,command,cpu,mem,threads,time,state
sample 12345 5 -file "$HOME/Desktop/LongCapture-idle.sample.txt"
```

取样只读调用栈，不需要辅助功能或输入监控权限，不重置屏幕录制授权。日志可能包含本机路径，请检查并去除个人信息后再分享。不要为了排查而清理系统 Vision 缓存、关闭安全机制或强制丢弃未保存结果。
